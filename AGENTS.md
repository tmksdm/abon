# Правила работы с Abon

## Перед началом этапа

1. Прочитать `APP_BRIEF.md`, `docs/PROJECT_STATE.md` и `docs/DECISIONS.md`.
2. Проверить `git status --short --branch`; не затирать пользовательские изменения.
3. Сформулировать один проверяемый результат этапа и не смешивать его с независимыми функциями.

## Технологии и структура

- React + TypeScript + Vite, мобильная PWA.
- Предметная логика не импортирует SDK конкретного backend; доступ к данным идёт через небольшой интерфейс репозитория.
- Даты хранения — календарные строки `YYYY-MM-DD`; преобразования дат и денег покрываются тестами.
- Не использовать `any`, глобальный state-manager и архитектурные слои без реальной границы.

## Дизайн

- Современный, спокойный, плотный и понятный интерфейс без декоративного шума.
- Светлая и тёмная темы автоматически следуют `prefers-color-scheme`; ручной переключатель добавлять только по подтверждённой потребности.
- Все цвета — через CSS custom properties; контраст текста не ниже WCAG AA.
- Никаких эмодзи. Если нужна пиктограмма, использовать только один набор Material Design Icons/Material Symbols через общий компонент `Icon`.
- Mobile-first от 320 px; основные действия доступны большим пальцем, но интерфейс не ломается на компьютере.

## Данные и безопасность

- Облако — источник синхронизации, локальная база — офлайн-копия, но не единственный экземпляр данных.
- Каждая запись принадлежит конкретному пользователю/залу; авторизация проверяется на доверенной стороне для каждой операции.
- Не коммитить `.env`, ключи сервисных аккаунтов, реальные клиентские данные и резервные копии.
- Импорт проверяет версию и структуру файла до записи; восстановление не удаляет текущую базу без явного подтверждения.
- Для изменений схемы обязательны миграция, обратная совместимость резервной копии и тест.

## Проверка и завершение этапа

- Перед коммитом выполнить `npm run check` и просмотреть `git diff --check` и `git diff`.
- Сообщения коммитов писать по-русски, простым языком и в прошедшем времени.
- После подтверждённого результата обновить `docs/PROJECT_STATE.md`; `docs/DECISIONS.md` менять только для значимых труднообратимых решений.
- Каждый завершённый этап — отдельный коммит и push в `main`, как явно попросил владелец проекта.
- В конце оставить ровно один следующий результат и точку входа для нового контекста.
